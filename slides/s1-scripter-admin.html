Pourquoi scripterLe quotidien d'un admin

À la main

  • 10 commandes tapées avant chaque intervention
  • oublis, fautes de frappe, « ça marchait chez moi »
  • aucune trace de ce qui a été fait
  • impossible sur 50 serveurs à 3 h du matin

Scripté

  • reproductible : même entrée, même résultat
  • traçable : logs, code versionné dans Git
  • planifiable : cron, systemd, supervision
  • relisible par un collègue ou un auditeur
En cybersécurité, un script est aussi une preuve : ce qui a été vérifié, quand et comment.

DémoMême tâche, deux langages : qui attaque en SSH ?

Bash : 1 ligne, lisible si on connaît les outils

grep "Failed password" auth.log.extrait \
  | grep -oE 'from [0-9.]+' \
  | sort | uniq -c | sort -rn

Et si on veut filtrer par heure, exporter en JSON, ou alerter au-delà de 10 échecs ?

Python : plus long, mais extensible

import re
from collections import Counter

MOTIF = re.compile(r"Failed password for (?:invalid user )?\S+ from (\S+)")

ips = Counter()
with open("auth.log.extrait", encoding="utf-8") as f:
    for ligne in f:
        if m := MOTIF.search(ligne):
            ips[m.group(1)] += 1

for ip, n in ips.most_common():
    print(f"{n:>5} {ip}")

AnatomieLa checklist du script « propre »

  • Shebang : #!/usr/bin/env bash
  • En-tête : rôle, usage, codes retour, auteur
  • --help : un collègue doit pouvoir s'en servir sans lire le code
  • Arguments plutôt que des valeurs en dur
  • Codes retour significatifs : 0, 1, 2
  • stdout pour le résultat, stderr pour les messages
  • Échec propre : un message clair, pas une trace
  • Aucun secret dans le code
  • Vérifier les prérequis : commandes, droits, fichiers
  • Idempotent si possible : le relancer ne casse rien
Point de départ : modeles/script_modele.sh et modeles/script_modele.py

Anatomiestdout, stderr et redirections

# stdout (1) : le RÉSULTAT, à exploiter
# stderr (2) : les MESSAGES, pour l'humain

./inventaire.py -f json > inv.json   # résultat seul
./inventaire.py 2> erreurs.log       # messages à part
./inventaire.py > tout.log 2>&1      # tout ensemble
./inventaire.py 2>/dev/null          # messages ignorés

# Le test qui ne pardonne pas :
./inventaire.py -f json | python3 -m json.tool

Erreur classique

Un print("Lecture de /proc…") de debug dans un script qui produit du JSON : la sortie n'est plus du JSON valide, et l'outil suivant plante.

En Python : logging configuré sur sys.stderr, et print() réservé au résultat.
S1 · Scripter l'administration15

AnatomieBash robuste : 5 réflexes

#!/usr/bin/env bash
set -euo pipefail   # erreur, variable vide, pipe : stop

fichier="$1"        # TOUJOURS des guillemets
[[ -r "$fichier" ]] || { echo "illisible" >&2; exit 2; }

command -v ss >/dev/null || echo "ss absent" >&2

tmp="$(mktemp -d)"
trap 'rm -rf -- "$tmp"' EXIT   # nettoyage garanti

while read -r ligne; do
  (( n++ )) || true
done < <(df -P)      # et non : df -P | while read
  1. set -euo pipefail en tête
  2. guillemets autour de chaque variable
  3. vérifier les prérequis (command -v, [[ -r ]])
  4. trap … EXIT pour nettoyer
  5. pas de | while si la boucle modifie une variable : c'est un sous-shell
Et shellcheck script.sh avant chaque commit.

AnatomiePython robuste : la structure type

#!/usr/bin/env python3
"""Rôle. Codes retour : 0 OK, 1 anomalie, 2 erreur."""
import argparse, logging, sys
from pathlib import Path

log = logging.getLogger("inventaire")

def lire_comptes(chemin: Path) -> list[dict]:
    ...                     # fonction pure : facile à tester

def main(argv=None) -> int:
    p = argparse.ArgumentParser(description="...")
    p.add_argument("-s", "--seuil", type=int, default=80)
    args = p.parse_args(argv)
    logging.basicConfig(stream=sys.stderr)
    try:
        comptes = lire_comptes(Path("/etc/passwd"))
    except PermissionError as e:
        log.error("droits insuffisants : %s", e)
        return 2
    print(comptes)
    return 0

if __name__ == "__main__":
    sys.exit(main())
  • main() renvoie le code retour
  • argparse : l'aide et la validation sont gratuites
  • pathlib.Path plutôt que des chaînes
  • des petites fonctions qui renvoient des données : la mise en forme vient après
  • subprocess.run([...], check=True, timeout=5) : jamais shell=True ni os.system

L'IA comme copilote

S1 · Scripter l'administration18

IACe qu'elle fait bien, ce qu'elle fait mal

Très utile pour…

  • un premier jet, ou un squelette
  • expliquer une commande, une regex, une erreur
  • traduire du Bash en Python (et l'inverse)
  • proposer des cas de test
  • relire, reformuler une documentation

Mais elle…

  • invente des options ou des fonctions qui n'existent pas
  • ignore votre contexte : version, OS, droits
  • propose des commandes destructrices sans prévenir
  • néglige les erreurs et les cas limites
  • est sûre d'elle, même quand elle a tort
S1 · Scripter l'administration19

IALes 5 règles du module

  1. Aucune donnée sensible dans un prompt : mots de passe, clés, IP ou noms réels, logs d'entreprise
  2. Vous comprenez tout ce que vous rendez : une ligne inexplicable n'a rien à faire là
  3. Vous testez dans un environnement jetable avant de faire confiance
  4. Vous vérifiez à la source : man, --help, documentation officielle
  5. Vous tracez votre usage dans JOURNAL-IA.md
Un journal honnête qui montre les erreurs de l'IA que vous avez corrigées vaut mieux qu'un journal vide.

IAUn prompt qui marche pour du scripting

fais-moi un script python qui analyse les logs ssh

Contexte    : Ubuntu 24.04, Python 3.12, lancé par cron
              en tant que root.
Tâche       : lire /var/log/auth.log et compter les échecs
              SSH par IP.
Contraintes : bibliothèque standard uniquement ; si le
              fichier est absent : message sur stderr,
              code retour 2.
Format      : un seul fichier, main(), argparse.
Demande     : explique chaque regex, puis propose 3 cas
              de test, dont 1 cas limite.
  • Contexte : OS, version, qui lance le script
  • Tâche précise, avec l'entrée et la sortie
  • Contraintes : dépendances, comportement en cas d'erreur
  • Format attendu
  • Demander des explications et des tests : c'est ce qui vous permet de vérifier

Démo en directPrompt → code → revue critique

Prompt naïf : « fais un script python qui affiche l'espace disque »

Que voyez-vous de problématique dans la réponse ?

Puis le prompt structuré : comparons.

Grille de revue : 5 questions

  1. Est-ce que je comprends chaque ligne ?
  2. Entrée absente, vide ou malformée : que se passe-t-il ?
  3. Quels effets de bord : écriture, suppression, réseau, droits ?
  4. Les commandes et options existent-elles sur ma version ?
  5. Comment je teste que ça marche, et que ça échoue proprement ?
L'IA répond à la question posée, pas à celle qu'on aurait dû poser.
